# Release v0.5.0 {#release_v0_5_0}

Released 2026-11-01. 421 commits since v0.4.0; 592 files changed.

Leadership decided by a majority with leases, a write-ahead log (WAL) the library replicates with one
writing thread, a matching engine that takes no decision alone, and both matching engines applying
every command from the WAL, so that losing the leading engine costs a short pause and nothing else.

New features are frozen while the design is restored, phase by phase, under
[the plan for restoring the design](../../recovery_plan.md). Phases 1 to 7 of that plan are finished.
Phase 8, both matching engines applying the WAL, is under way: its first design is built, and three of
the five steps of its second design, [voided commands](../../availability/voided_commands.md), are built.
[Project status](../../project_status.md) says what works, what is known to be wrong, and where to start.

`CHANGELOG.md`, in the repository root, carries the full list. Not linked from here: it is not
one of doxygen's inputs, so a link to it cannot be resolved and warnings are fatal.

## Highlights

### Leadership is decided by a majority, with leases

An instance of a pair leads only while a majority of three voters has granted it a lease that has not
run out. For a component pair the voters are the two instances and the arbiter pool; for the arbiters
they are the two arbiters and the witness. A voter keeps each promise in a record on disk, so that a
voter that restarts cannot promise the same period to the other instance. The design is checked with TLC
against TLA+ models, in `docs/availability/tla`.

### The library replicates the WAL, with one writing thread

The sequencer keeps its WAL through the library's `ReplicatedWal`, whose thread is the only one that
writes it. A follower sequencer, a matching engine catching up and a publisher starting late in the day
all follow the WAL through the library, on a thread of their own, so none of them stops the venue
answering orders. The build refuses any new read of the WAL in the sequencer that is not in a named
table of permitted reads, each with its reason.

### Tests read test events, not the wording of log messages

Each component sends events saying what it did, on a connection a test opens. Every check
`ha_test.py` makes is on a test event, on what a member receives, or on the WAL files, so rewording a
message in a Quill log breaks no test.

### The matching engine takes no decision alone

Every decision the matching engine takes is a command in the WAL: cancelling the book, halting trading
and resuming it. Its OrderID and ExecID values are made from positions in the WAL, so an engine that
applies the same commands gives the same identifiers. `wal_replay_check` applies a sequencer's WAL to
a fresh engine and requires every report it produces to be in the WAL as the engine sent it, and every
scenario runs both matching engines on its WAL afterwards and requires them to agree.

### Both matching engines apply the WAL

The engine that does not lead applies every command from the WAL itself, keeps its reports until the
WAL holds the leader's, and compares the two. An engine whose reports differ from the leader's does
not lead. A promoted engine keeps every order: the book it takes the lead with is the one the members
were told of, so nothing is cancelled on promotion.

### A command that crashes both engines is voided, and orders wait for an engine

Once both engines apply every command, a command that crashes one crashes both. An engine that died
applying a command asks, when it restarts, for that command to be voided, unless its peer applied it;
the leading sequencer writes the void into the WAL, and the member is sent a rejection.

While no matching engine leads, the leading sequencer holds every order and cancel in its WAL and
sends them to no engine. The engine that next leads is caught up to the position before the first
held order and is then sent the held orders live, so each member receives a first report, not a
resend. Once no engine has led for five seconds, the gateways refuse new orders and cancels with a
reason, and they accept again on their own when an engine leads. In the full runs of the scenarios a
plain failover of the leading engine held orders for 4.9 seconds with the primary engine leading
first and 3.0 seconds with the secondary first.

### Every command sent while the sequencers change leader is answered once

A gateway keeps each command until it is answered, and sends every one still unanswered to a new
leader when it learns of one. Before this, orders sent while the sequencers changed leader were lost
without a reply.

### The scenarios

`ha_test.py` has 93 scenarios, and all 93 pass with the primary matching engine leading first, as do
the 35 that also run with the secondary leading first.

## Upgrading from 0.4.0

- Every environment declares, in its `[shared]` section, `[recovery] orders_held_at_most_seconds` (5)
  and `[recovery] automatic_recovery_limit_seconds` (10), which both sequencers of the pair read.
- `[absence] absence_limit_seconds` moves into the sequencer's configuration, declared once in each
  environment; `[order_book] absence_limit_seconds` in the matching engine is gone.
- `order_book.open_orders_on_promotion` is gone: a promoted engine keeps every order.
- Each matching engine needs `[identifiers] secret_file`, which `deploy.py` writes where none exists.
- The sequencer's `[wal] records_kept_for_publishers` and `bytes_kept_for_publishers` size the copy of
  committed records the publishers are sent from.
- OrderID and ExecID values change form, from `ME-ORD-N` and `ME-EXEC-N` to a letter and 16
  hexadecimal digits.
- `OrderAcceptance`'s fields are `held_order_count` and `no_engine_for_seconds`.
- The open-order region's header is version 4, and a region written by 0.4.0 is not read.
- Many PDUs changed. There is no compatibility between 0.4.0 and 0.5.0 components on the wire.

## Known limitations

- 80 bugs are open, 18 of them high severity. See the [bug list](../../bug_list.md).
- When the limit on automatic recovery halts trading, the orders held while no engine led are not yet
  rejected, and an operator has no way yet to declare a halt or lift one. Steps 4 and 5 of
  [voided commands](../../availability/voided_commands.md) are the work that does both
  ([BUG-0197](../../bug_list.md#bug_0197)).
- A matching engine that is connected but has stopped working looks healthy
  ([BUG-0194](../../bug_list.md#bug_0194)).
- The write-ahead log retains everything and nothing reclaims it
  ([BUG-0048](../../bug_list.md#bug_0048)).
- 120 of the 151 requirements have no scenario checking them
  ([BUG-0068](../../bug_list.md#bug_0068)).
- A lease promise record can take longer to write than a lease period on a busy disk, and the leader
  then loses its lease ([BUG-0167](../../bug_list.md#bug_0167)).
- The pause tests of the reactor fail in the coverage build and in the Rocky 8 container, so neither build completes
  with them included ([BUG-0184](../../bug_list.md#bug_0184)).

## Release check

This release was checked with `release_check.py --skip ha --skip perf`.

- **The high availability scenarios were not run by the release check,** because both full runs of them had just
  passed on the same code: all 93 with the primary matching engine leading first, and all 35 that also run with the
  secondary leading first.
- **The performance run was not part of it.** `perf_run.py` runs only with the machine switched into measurement mode,
  and it was not.
- **Passed:** a clean working tree, the version agreeing in every place it is stated, the coding standards, a full
  clean build with Java, Doxygen and every test suite, the deployment scripts, and every installed binary resolving
  its shared libraries.
- **Coverage failed before it measured anything,** because one test failed in the coverage build:
  `PauseReadingIntegrationTest.APausedInboundConnectionDeliversNothingUntilItIsResumed`. Run ten times, the pause tests
  failed in four runs of the coverage build and in none of the ordinary build. It is
  [BUG-0184](../../bug_list.md#bug_0184), open since 19 October 2026.
- **The Rocky stage, gcc 8.5:** everything compiles, and every unit, codec, cryptography and application test passes.
  Of the integration tests, all pass but the pause tests of BUG-0184, which failed in each of two runs in the
  container, so the stage itself fails. Run again with only those tests left out
  (`GTEST_FILTER=-PauseReadingIntegrationTest.*`), the container's build, release and deploy steps all complete.
  Reaching the compiler needed [BUG-0219](../../bug_list.md#bug_0219) fixed: five scripts needed TOML support to
  answer `--help`, which the container's Python 3.8 does not have, so for 0.4.0 the stage stopped before compiling.
