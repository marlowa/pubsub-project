# Release v0.6.0 {#release_v0_6_0}

Released 2026-11-21. 304 commits since v0.5.0; 697 files changed.

A trading day that starts, moves through its phases and ends by itself, with every open order cancelled at the
close and every component's files archived at the end; gateways that bound what they have read and not yet
answered, so that overload no longer costs the leading sequencer its lease; and a matching engine and a sequencer
that hold their memory from the start of the day and do not call the heap allocator on the order path.

New features are frozen while the design is restored, phase by phase, under
[the plan for restoring the design](../../recovery_plan.md). Phases 1 to 11 of that plan are finished, and phase 12,
returning to the bug list, is under way. The trading day was built during phase 12 because the bug list needed it:
open orders were never cancelled at the end of the day, and one day's files were taken as a restart on the next,
which broke principles V2 and V12. [Project status](../../project_status.md) says what works, what is known to be
wrong, and where to start.

`CHANGELOG.md`, in the repository root, carries the full list. Not linked from here: it is not one of doxygen's
inputs, so a link to it cannot be resolved and warnings are fatal.

## Highlights

### The trading day

Every phase, from the start of day through pre-open, open and the close to the end of day, is entered in order and
once, either on an operator's request with `scripts/trading_phase.py` or at the time in the day's schedule, which
the leading sequencer holds and follows. Members' new orders and cancels are accepted only in pre-open and open, and
every member is told of each change of phase. The close cancels every order still open and sends each member a
report of each cancel, which the sequencer writes into the WAL before the end of day begins. Every technical event
is published on the `technical_events` topic. See [trading phases](../../venue/trading_phases.md).

### The day starts fresh and ends by itself

`scripts/trading_day.py start` checks that no file of an earlier day is present, writes the run manifest and starts
the day. Each component is given the trading day on its command line and refuses a file written on another day. The
end of day is two events in the WAL: the first ends trading, and the leading sequencer writes the second once every
copy of the WAL is complete, or once a limit of time has passed. On the second, every component shuts itself down,
keeping a file of its last trading state, and its launcher archives its files. See
[starting and ending the trading day](../../venue/start_and_end_of_day.md).

### Overload no longer costs the lead

Each gateway limits the commands it has sent and not yet had answered, the messages waiting from each member
connection, and the members connected to it, and its command queue is sized from those settings. The matching engine
pauses reading commands while too many of its reports wait to be written, and cancels many orders in pieces of
2,000. The framework limits the messages waiting from one connection in a thread's queue, and one read hands on at
most 64 messages. Leases are renewed between messages however much work is queued, and a record read from far back
in the WAL is no longer reread on the sequencer's own thread.

### Memory is held from the start of the day

The matching engine locks its order map and its open-order region into memory before it is ready, and the sequencer
locks its record of command identifiers; either refuses to start, at Critical, if the memory cannot be locked, so a
shortage is found at the start of the day instead of ending the process in the middle of it. Removing an order from
the order map shifts later entries back, so the map is never copied during the day. The leading sequencer keeps no
map of which session placed each order, and the following matching engine keeps its reports in a block allocated at
the start. `scripts/heap_allocation_count.py` shows whether the order path calls the heap allocator.

### A queue grows without a lock, as a TLA+ model shows to be safe

A pool is added to a queue's allocator without the mutex that used to protect it. The TLA+ model
`docs/framework/tla/PoolChain.tla`, checked with TLC over 11.7 million states, shows the lock-free append safe, and
catches both faults put into it on purpose. A queue that has to grow is logged at Error and counted.

### An operator halts trading and lifts the halt

`scripts/operator_halt.py` sends a halt request to both sequencers over TLS with a client certificate. When no
matching engine could be trading within the longest recovery the venue does by itself, the venue halts on its own,
rejects the orders it held and cancels the book; a halt stays until an operator lifts it.

### The scenarios

`ha_test.py` has 118 results with the primary matching engine leading first, and 49 with the secondary leading
first, and all of them pass.

## Upgrading from 0.5.0

- **Every component is started with `--trading-day D`**, and the day is started with `scripts/trading_day.py start`.
  `devenv.py` does both for the development environment.
- **Each environment file needs** `[paths] archive_dir`; the `[operator_certificates]` section and each sequencer's
  `operator_*` settings; `end_of_day_longest_wait_for_copies_seconds` in its shared section; for each gateway
  instance, `members_most_connected`; and for each sequencer, `identifiers_reserved`. Compare with
  `environments/dev.toml`.
- **Each component's configuration needs `last_state_file`**, each component that follows the trading day a
  `[technical_events]` section naming both publishers, each gateway a `[members]` section, and each sequencer an
  `[end_of_day]` section. The binary gateway's `[members]` section also sets `messages_waiting_each`. Compare with the
  files under `applications/`.
- **The host must let the venue's user lock memory**: the matching engine locks its order map and region, and the
  sequencer its record of identifiers. See `docs/operations/locked_memory_requirement.md` for the figure and how to
  set the limit. A Docker container needs `--ulimit memlock=-1:-1`.
- **The filesystem holding the WALs and the open-order regions must be mounted `lazytime`**, preferably on a disk of
  its own; see `docs/operations/filesystem_requirements.md`.
- **Remove** the `[absence]` section and `absence_limit_seconds`, and the gateways' `[open_order_pool]` settings.
- **The Rocky 8 image** is built with
  `docker build -t pubsub-rhel8 --build-context tla2tools=$THIRDPARTY_DIR/tla2tools-1.8.0 .`, with
  `tla2tools.jar` from release 1.8.0 of the TLA+ tools in that directory.
- **On Rocky or Red Hat 8**, a relative install directory in the environment file is taken to be
  `installed-rocky8` or `installed-rhel8`, the directory the build stages into there.
- **Many PDUs changed**, `WalRecord` among them, which gains `produced_by_seq_no`. There is no compatibility between
  0.5.0 and 0.6.0 components on the wire, and a WAL written by 0.5.0 is not read.

## Known limitations

- 52 bugs are open, 4 of them high severity. See the [bug list](../../bug_list.md).
- A trading halt cannot be applied to one instrument ([BUG-0065](../../bug_list.md#bug_0065)).
- A matching engine that is connected but has stopped working looks healthy
  ([BUG-0194](../../bug_list.md#bug_0194)).
- Every resend request reads the whole day's WAL on the thread that sequences orders; the recovery service that
  replaces it, keeping the most recent 100,000 messages for each member, is designed and not built
  ([BUG-0113](../../bug_list.md#bug_0113)). The WAL is never reclaimed during the day
  ([BUG-0048](../../bug_list.md#bug_0048)).
- Most requirements have no scenario checking them ([BUG-0068](../../bug_list.md#bug_0068)).
- Under overload the follower sequencer still falls behind its leader, so the leader runs alone for part of the time
  ([BUG-0264](../../bug_list.md#bug_0264)).
- The order activity recorder is not built, so the end of day waits for no external record of the day's events.
