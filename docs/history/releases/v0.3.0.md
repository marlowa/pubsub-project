# Release v0.3.0 {#release_v0_3_0}

Released 2026-08-10. 89 commits since v0.2.1; 282 files changed.

A trading-day load profile, a reconnecting member sent the reports it missed, and both
gateways renamed for what they actually are.

`CHANGELOG.md`, in the repository root, carries the full list. Not linked from here: it is not
one of doxygen's inputs, so a link to it cannot be resolved and warnings are fatal.

## Highlights

### A trading day, rather than a steady rate

`perf_run.py --profile profiles/trading_day.toml` runs a shaped day: pre-open, an opening
auction at the ceiling, a steady morning, a sustained elevated hour, a midday lull, an
afternoon burst and a close above the ceiling — with a cancel stream, so the book reaches a
working size instead of only growing. Phase rates are fractions of a measured ceiling, so the
same profile means the same thing on a machine of a different size.

It is the reason almost everything else here was found: nine runs of up to two hours each,
exercising the framework through load transitions no steady rate produces.

### A reconnecting member is sent the execution reports it missed

A ResendRequest is now answered with the real reports, carrying `PossDupFlag=Y` and
`OrigSendingTime`, and only the administrative remainder is gap-filled — the split FIX actually
prescribes. Previously every ResendRequest was answered with a blanket
`SequenceReset-GapFill`: the session survived and the member was told nothing about what had
become of its orders.

Underneath it, sequence continuity across a reconnect, without which a member never thinks to
ask. A session's outbound number is reported to the sequencer when it unbinds and handed back
when a gateway binds it, so a reconnect — to the same instance or to the backup — continues the
member's numbering instead of restarting at 1. `ResetSeqNumFlag=Y` is honoured for the member
that wants the opposite.

The replay is a filtered WAL scan rather than a second copy of anything: 18 ms to scan a 4 MB
retained WAL and return 3,223 records for one session.

### Both gateways renamed for what they are

`order_gateway` is now `fix_order_gateway`, and `binary_gateway` is `binary_order_gateway`.
The old names said which wire format a gateway spoke, or did not say anything; neither said
what kind of gateway it was, and order entry is not the only kind a venue needs. A gateway
carrying nothing but risk-parameter changes should not have to compete with members placing
orders. The change runs all the way through: directories, binaries, CMake targets, namespaces,
class names, config files, component names, deployed paths and docs.

### Latency you can see

The order round-trip histogram is charted as percentile bands over time against a stated
ceiling, with an exact count of the orders that exceeded it — refused rather than estimated
when no bucket bound sits on the ceiling value. `--from` / `--to` scope a chart to one run or
one incident.

Bucket bounds now reach 250s, covering a third regime: an order caught across a failover. A
trading-day run put 223,824 orders (1.87%) past the old 5s top bound, where the histogram could
say only "more than five seconds"; the `_sum` series puts their mean at 62s or more.

### A logon that raced the venue's own links

A FIX logon arriving before the gateway's sequencer links were up waited five seconds for a
session the venue had already granted, then opened it on numbering the sequencer never
confirmed. The gateway now re-announces every session still awaiting its numbering as each
sequencer link is established. The five-second path remains as a backstop rather than the
ordinary way out of the race.

`ha_test.py` could not have caught this even with a longer wait — its budget was shorter than
the recovery it was waiting for, and a session opened on unconfirmed numbering was
indistinguishable from a healthy one at the instant of logon. It now fails the scenario when
the fallback is what rescued the session.

### Release engineering

The release check gained a `runnable` stage that catches a tree of binaries built for the wrong
platform in 0.2 seconds, rather than ten minutes into the high-availability stage where it
looked like a catastrophic regression. Release artefacts now name the platform they were built
for, and the Rocky container no longer deploys its RHEL8 binaries over the development host's
install tree.

## Known limitations

- Coverage is measured on the development host only. The Rocky container answers a different
  question, and a baseline is toolchain-specific.
- The Rocky image shares RHEL8's gcc but not its Python, so pylint, pytest and the pybind11
  extension build still need checking on the real target.
