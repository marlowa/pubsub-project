\chapter{The applications built on the library}
\label{ch:applications}

The library is exercised by a set of applications that resemble the components
of a trading venue: gateways, a sequencer, a matching engine, an authentication
service and a publisher.

\textbf{They are not a trading venue, and are not intended to become one.} They
exist to put the library under the kinds of load and failure a venue produces,
which is a different purpose from trading. The matching engine, for instance,
accepts and cancels orders and does not match them. Absences of that kind are
deliberate, and this chapter records which they are, so that a reader can tell
them from defects.

This chapter currently describes the matching engine publisher and specifies
the order gateways' cancellation requirements and limits on how quickly a
member may send orders. It also states the required behavior for instrument
reference data and the Instrument Reference-data Editor (IRE). That behavior
is not yet implemented. Requirements for the other applications have not yet
been added.

\section{The order gateways}
\label{sec:order_gateways}

Two gateways accept orders from members. The FIX gateway speaks FIX 5.0 SP2 over a
FIXT.1.1 session. The binary gateway speaks an encoding of the venue's own. Members are
moving towards the binary gateway for its lower latency, and both are expected to remain.

\subsection{The fields a request to cancel must carry}
\label{subsec:cancel_required_fields}

FIX 5.0 SP2 requires four things on an OrderCancelRequest: ClOrdID, the instrument, Side
and TransactTime. It makes OrigClOrdID optional, because a member may instead name the
order by the OrderID the venue assigned it. It makes the quantity optional as well.

The venue identifies a member's order by the identifier the member submitted it under. The
matching engine keys its book on that identifier, and the venue offers a member no other
way to name an order it has placed. A request to cancel therefore carries it.

\begin{requirement}{R-0142}{A request to cancel an order names the order it cancels}
  A request to cancel an order shall carry the identifier the order was submitted under.
  The venue shall refuse a request that omits it.
  \rationale{The identifier on the cancel request is the request's own, not the order's.
  A request carrying only that identifier names nothing the venue can look up.

  FIX permits a member to name the order by the identifier the venue assigned instead.
  The venue does not accept that alternative, because the matching engine's book is keyed
  on the member's identifier and holds no index on its own.}
  \uncovered{no scenario sends a cancel that omits the original identifier}
\end{requirement}

The venue requires nothing else beyond what FIX requires. In particular it does not
require the order's quantity. A cancel applies to the whole of an order, so the quantity
cannot change what the venue does with the request, and a member that sends one is sending
a field the venue reads and discards.

\begin{requirement}{R-0144}{Both gateways accept the same request to cancel}
  The two gateways shall require the same fields on a request to cancel an order. Where
  FIX 5.0 SP2 makes a field optional, the venue shall accept a request that omits it,
  unless this document states a requirement for that field.
  \rationale{A member choosing between the two gateways is choosing on latency. A member
  that has to send different messages to the two of them is choosing on message format as
  well, and a member moving from one to the other has to change its code to do it.

  The requirement is written as a rule about the pair rather than as a list of fields,
  because the fields will change and the agreement between the gateways is the property
  worth keeping.}
  \uncovered{no scenario sends the same cancel to both gateways}
\end{requirement}

\subsection{What a member is told about a message the venue will not process}
\label{subsec:refused_message_reply}

A member that sends a message the venue refuses is told so. The gateways answer a refused
new order with an execution report that rejects the order. A request to cancel that a gateway
refuses itself, before it reaches the matching engine, is answered with a reply that refuses
the request and says nothing of the order: in FIX, a session-level Reject. A request to cancel
that the matching engine refuses is answered with an OrderCancelReject reporting the order's
status. Each answer names the reason, such as the fields that were missing.

\begin{requirement}{R-0143}{A message missing a field the venue requires is answered}
  Where the venue refuses a member's order or request to cancel because a field the venue
  requires is absent, the venue shall answer the member, and shall name the absent fields.
  Where the message omits the identifier the answer would be addressed by, the venue may
  discard it.
  \rationale{A member whose message is discarded without a reply cannot tell refusal from
  loss. Of the two readings, the member takes the one where the message is still being
  acted on, which is the more dangerous. A member that believes a cancel was accepted, and
  whose order is in fact still resting, is exposed to a market it believes it has left.

  Naming the absent fields is what makes the answer usable. A member told only that fields
  were missing has to search a message of thirty fields for the one the venue objected to,
  and the venue already knows which it was.

  The exception is narrow. A rejected order is answered with a report addressed by the
  identifier the member put on the order, so an order without one cannot be answered. A
  refused request to cancel is answered with a reply that names the message itself, so it is
  answered whether or not it carries an identifier.}
  \uncovered{no scenario sends a message with a required field absent}
\end{requirement}

\begin{requirement}{R-0151}{A refused request to cancel is not answered as a rejected order}
  Where a gateway refuses a member's request to cancel or amend an order, before it reaches
  the matching engine, it shall answer with a reply that refuses the request and says nothing
  of the order. In FIX, the reply shall be a session-level Reject naming the refused message.
  Where the matching engine refuses the request, the reply shall be an OrderCancelReject
  reporting the order's current status, which is Rejected for an order the venue does not
  hold.
  \rationale{The order a refused request names may still be on the book. FIX gives an
  execution report rejecting an order one meaning: that the order is not on the book. A
  member that receives one in answer to a cancel believes it has no order in the market,
  while the venue can still trade the order it holds. A member exposed to a market it
  believes it has left is the most dangerous outcome a reply can produce.

  Only the component that holds the order can say what its status is. A gateway that
  refuses a request before the matching engine sees it does not know the order's status, so
  it says only that the request was refused. This is how Euronext answers a message its
  gateway refuses: with a session-level Reject, which carries no order identifier because
  the matching engine never processed the message. An OrderCancelReject, which FIX requires
  to carry the order's status, comes only from the matching engine.

  The rule holds whatever the reason for refusing the request: a missing field, the venue
  not accepting orders, or a limit on how fast the member may send (\reqref{R-0150}).}
  \covers{ha_test:42}
  \covers{ha_test:56}
\end{requirement}

\begin{requirement}{R-0152}{Both gateways refuse the same commands for the same reasons}
  Each gateway shall check a member's order or request to cancel before passing it to the
  sequencer, and shall refuse one that has a required field empty, an enumerated field
  holding a value the venue does not define, a quantity or price that is not a decimal
  number, or an identifier, symbol or quantity longer than the venue holds. Each gateway
  shall also refuse an order or request to cancel while no sequencer is connected or the
  venue is not accepting orders. A refusal shall be answered, and shall say why.
  \rationale{A member cannot be held to two sets of rules according to the protocol it
  happens to speak. A command passed on unchecked is worse than one refused: an identifier
  longer than the matching engine's book key is cut short there, so two orders can become
  one, and a command the engine cannot read is dropped with no reply at all.

  A binary command has to be decoded to be checked, which the FIX gateway's parsing
  already does. Decoding fields at fixed positions costs less than parsing FIX text, so
  the binary gateway keeps its advantage.}
  \covers{ha_test:57}
  \covers{ha_test:42}
\end{requirement}

\subsection{How fast a member may send}
\label{subsec:gateway_throttles}

The venue limits how fast each session may send three kinds of command: placing an order,
amending an order and cancelling an order. Each limit is a number of commands per second.
The venue provisions the limits for each comp id, and the gateways apply them to each
session separately. The design is in \texttt{docs/venue/gateway\_throttles.md}.

\begin{requirement}{R-0148}{Each session is limited in how fast it may place, amend and cancel}
  The venue shall hold, for each comp id, a limit on the number of commands per second for
  each of placing, amending and cancelling an order. Each limit shall be a whole number from
  0 to 100,000, where 0 means the commands of that kind are not limited, and 0 shall be the
  value of a limit nobody has set. The gateways shall apply a comp id's limits to each of its
  sessions separately, with the values that held when the session logged on.
  \rationale{A member sending faster than the venue can serve takes capacity from every
  other member. A limit for each comp id lets the venue give each member the rate it has
  agreed to, and nothing beyond it.

  The limits apply to each session separately because the gateways count commands where
  they arrive. Counting across all the sessions of a comp id would need the gateways to
  share their counts with each other, on every command.

  The venue processes an order from start to end in tens of microseconds, so 100,000
  commands per second, one every 10 microseconds, is the fastest rate any member could
  use. Amending is limited although the venue cannot yet amend an order, so that amending
  is limited from the day it exists.}
  \covers{ha_test:56}
\end{requirement}

\begin{requirement}{R-0149}{A limit holds over every one-second period}
  A gateway shall accept a command only if fewer commands of the same kind than the limit
  were accepted on the session during the second before it arrived. A command the gateway
  refuses shall not count towards the limit.
  \rationale{Measuring over the second before each command means no one-second period,
  wherever it starts, contains more commands than the limit. A count that started again at
  each whole second would allow twice the limit across the boundary between two seconds.

  A member that keeps sending while it is being refused would never be accepted again if
  its refused commands counted. Only accepted commands use the capacity the limit
  protects.}
  \covers{ha_test:56}
\end{requirement}

\begin{requirement}{R-0150}{A command over the limit is refused, and the member is told why}
  A gateway shall refuse a command that would exceed its session's limit, and shall answer
  the member with the reason, naming the limit. The gateway shall not pass the command to
  the sequencer, shall not hold it to send later, and shall keep the session open.
  \rationale{A member must be able to tell a refused command from a lost one, for the reason
  \reqref{R-0143} gives. A command held and sent later would reach the matching engine at a
  time the member did not choose, against a market that may have moved. Closing the session
  would cancel the member's resting orders under cancel-on-disconnect, which is a far
  heavier consequence than sending too fast.}
  \covers{ha_test:56}
\end{requirement}

\section{Instrument reference data and intraday changes}
\label{sec:instrument_reference_data}

The venue has a list of the instruments for which it accepts orders. Each
trading day starts from a complete snapshot of that list for the day's
\texttt{business\_date}. An instrument record has an \texttt{instrument\_id},
a \texttt{symbol} for reference, and an \texttt{expiry\_date}. Prices are not
part of the current reference data; they may be added when the venue uses
price bands.

The IRE maintains the reference data and sends changes to the sequencer. It
does not send them directly to a matching engine. The sequencer places
accepted changes in the WAL, which establishes their order relative to orders.
The matching engines apply the same changes from that log. The IRE identifies
each request with an \texttt{externalSystemRequestId}, which the answer echoes.
Its \texttt{event\_created\_ts} is the time the IRE created the request; the
position in the WAL, not this timestamp, determines when an accepted change
takes effect.

\subsection{The day's instrument list}

The snapshot for a trading day is the complete set of instruments tradable
that day. It replaces the preceding day's set: an instrument absent from the
new snapshot is no longer tradable. The snapshot's business date is the date
of the run. Every instrument has one venue-assigned identifier; members name
the instrument in an order by that \texttt{instrument\_id}, not by its symbol.

\begin{requirement}{R-0178}{The complete instrument snapshot is applied before pre-open}
  For each trading day, the venue shall apply the complete instrument snapshot
  for that day's business date before entering \texttt{pre\_open}. Every
  matching engine shall apply the same snapshot in WAL order. The venue shall
  validate the whole snapshot before applying it, and shall not enter
  \texttt{pre\_open} on a partial, invalid, or wrong-date snapshot. An
  instrument whose expiry date is before the business date shall not be in the
  tradable list.
  \rationale{A member must not be able to place an order against a list that
  is only partly loaded, and a promoted matching engine must make the same
  decision as the one it replaces. The business date is part of the day's
  input, rather than a value each process derives from its own clock.}
  \uncovered{no scenario loads, rejects, or interrupts an instrument snapshot}
\end{requirement}

\begin{requirement}{R-0179}{An order names a tradable instrument by its identifier}
  A member's order shall name its instrument by \texttt{instrument\_id}.
  The venue shall refuse an order whose identifier is not in the current
  trading day's tradable list, and shall tell the member why it was refused.
  The venue shall accept an instrument through its \texttt{expiry\_date},
  inclusive, and shall not accept it on a later trading day.
  \rationale{A venue-assigned identifier names one instrument without relying
  on a free-text symbol. The snapshot defines which instruments are available
  today; expiry bounds the last day on which the instrument may be traded.}
  \uncovered{no scenario places an order by instrument identifier, names an
  unknown instrument, or crosses an instrument's expiry date}
\end{requirement}

\subsection{Changes made during the trading day}

The IRE can add an instrument, replace an instrument's attributes, or remove
an instrument. A replacement is a whole record: it carries the existing
\texttt{instrument\_id}, \texttt{symbol}, and \texttt{expiry\_date}. The
identifier selects the record and cannot itself be changed by replacement.
Prices are not included. A replacement whose expiry date is before the
current trading day is refused.

\begin{requirement}{R-0180}{An instrument update changes exactly one valid record}
  The venue shall reject an attempt to add an \texttt{instrument\_id} already
  in the tradable list, or to replace or remove an identifier that is not in
  that list. It shall reject an add or replacement that omits the symbol or
  expiry date, or gives an expiry date before the current trading day. A
  replacement shall not change the identifier and shall replace the whole
  record for that identifier. A rejected update shall leave the list unchanged.
  \rationale{A failed edit must not leave the IRE and venue showing different
  data. Requiring a complete replacement record gives every omitted field one
  meaning: the request is invalid, not an instruction to retain an old value.
  A removed identifier may be added again, so an operator can recover from a
  mistaken removal.}
  \uncovered{no scenario checks invalid add, replace, or remove requests, or
  verifies that a removed identifier can be added again}
\end{requirement}

\begin{requirement}{R-0181}{Accepted updates take effect in WAL order}
  The IRE shall send instrument updates to the sequencer. The sequencer shall
  place each accepted update in the WAL, in the same order as member orders.
  The update shall affect orders sequenced after it, and shall not change
  the instrument state used for orders sequenced before it. Matching engines
  shall apply the updates from the WAL. Each request shall carry an
  \texttt{externalSystemRequestId} and an \texttt{event\_created\_ts} set when
  the IRE creates it; every answer shall echo the request identifier. The
  timestamp shall not determine the update's order or effective time. The IRE
  shall receive a successful answer only
  after the leading matching engine has applied the update; for a removal,
  this is after the resulting cancellation reports have been recorded for
  normal delivery. The IRE shall not communicate directly with a matching
  engine.
  \rationale{The WAL gives every order and reference-data change one shared
  order. An answer after application tells the IRE when the change is active.
  Waiting for member connections to receive reports would make completion
  depend on whether every member is connected; the reports instead use the
  venue's normal delivery and recovery behavior. The follower catches up from
  the WAL before it may lead.}
  \uncovered{no scenario orders around an update or checks the IRE's answer
  against WAL commitment, engine application, and report delivery}
\end{requirement}

\begin{requirement}{R-0182}{Removing an instrument cancels only its resting orders}
  When a removal takes effect, the venue shall refuse new orders for that
  instrument, cancel every order still resting in it, and record a cancellation
  report for each order for delivery to its member. It shall then remove the
  instrument from the tradable list. It shall not halt the instrument or the
  market, and shall continue accepting orders in every other tradable
  instrument.
  \rationale{Removing one instrument from the available set is not a response
  to a market fault. Orders resting in the removed instrument must not remain
  live, while unrelated instruments and their members must not be affected.}
  \uncovered{no scenario removes one instrument with resting orders while
  checking its cancellations and continued trading in another instrument}
\end{requirement}

\begin{requirement}{R-0183}{An instrument expires after trading on its expiry date}
  An instrument shall remain tradable throughout its expiry date. At the
  close of that trading day it shall no longer be tradable, and shall not be
  present in the next trading day's tradable list. The venue's ordinary close
  shall cancel its resting orders under \reqref{R-0172}; expiry shall not cause
  a separate market halt.
  \rationale{The expiry date is inclusive. The venue already cancels every
  resting order at the daily close, so expiry changes the instrument set for
  the next day rather than creating a second close procedure.}
  \uncovered{no scenario trades an instrument on its expiry date and verifies
  it is unavailable on the following trading day}
\end{requirement}

\subsection{Rate limiting IRE updates}

The IRE's update rate is limited to protect the sequencer and matching
engines. The limit is configurable. Updates above it are refused rather than
held for later or combined with another update.

\begin{requirement}{R-0184}{The rate of instrument updates is configurable and bounded}
  The venue shall limit the number of instrument update requests it accepts
  from the IRE in any one-second period, using a configurable limit. An update
  over the limit shall be refused immediately, shall not change the instrument
  list, and shall receive a rate-limit answer correlated by
  \texttt{externalSystemRequestId}. The venue shall not queue the refused
  update or combine it with another update.
  \rationale{An update stream must not consume an unbounded share of the
  sequencer's capacity or leave the IRE unable to tell when a delayed update
  will take effect. Refusing an update explicitly lets an operator decide
  whether and when to retry it.}
  \uncovered{no scenario exceeds a configured IRE update limit and checks the
  refusal, unchanged state, and continued order processing}
\end{requirement}

\section{The matching engine publisher}
\label{sec:matching_engine_publisher}

The matching engine publisher (MEP) follows the sequencer's write-ahead log,
stores the records in its own log, and serves two topics: \texttt{orders} and
\texttt{execution\_reports}. The MEP is currently the venue's only publisher.
\texttt{topic\_probe} is the only implemented subscriber. The Order Activity
Recorder (OAR) is planned as another subscriber to the execution-report topic,
but the OAR application has not yet been written.

\subsection{What it publishes}
\label{sec:mep_pubsub}

The \texttt{orders} topic carries \texttt{NewOrderSingle} and
\texttt{OrderCancelRequest} messages. The \texttt{execution\_reports} topic
carries \texttt{ExecutionReport} messages. Each record retains the sequence
number assigned by the sequencer. The record therefore has the same position
in the logs of both MEP instances, allowing a subscriber to resume from its
position after failover.

The MEP sends each record separately to each subscriber over that subscriber's
own unicast connection. The alternatives considered and the reasons for
rejecting them are described in \cref{sec:pubsub_alternatives}.

\subsection{Technical events}
\label{sec:mep_technical_events}

Whether the MEP publishes technical events remains undecided. The venue-level
requirement and the unresolved choice of how to distribute these events are
described in \cref{sec:ha:technical_event}.
